# mutation testing 実験：0001 cart-add-item

CHARTER の方針「mutation testing は、1機能に1回だけの実験にして、効果を見てから常設するか決める」に沿った、1回目の記録。
題材は 0001（カートに商品を追加する。テスト16件、`make check` 通過済み）。ツールは mutmut 3.8.0。

## 結論（先に）
- **効果はあった。** 2秒で、テストの穴を3種類見つけた（人間もAIも気づいていなかった）。
- **ただし、今の `src/` の構造では、ツールがほとんど測れなかった。** 本体のまま回すと mutant は5件だけ。ロジックを関数に切り出した測定用コピーで、初めて60件になった。
- **常設（`make check` への組み込み）はまだしない。** 手動で回す `make mutate` だけ用意する。理由は下の「判断」。

## 何をしたか
1. 本体（`src/cart_api/main.py`）に mutmut を流した → **5件**（killed 3、survived 2）。
2. 理由を調べた。mutmut 3 は、関数・メソッドの本体だけを変異させる。`create_app()` の中の入れ子関数（`add_item`、例外ハンドラ）と、モジュール直下の定数（`MAX_QUANTITY`、`PRODUCTS`）、`Field(ge=1, le=...)` は対象外。0001 の本当のロジックは、ほぼこの対象外の場所にあった。
3. **測定用コピー**（リポジトリの複製。本体は変更していない）で、`create_app()` の中のロジックを `add_to_cart()` と `error_body()` に切り出した（挙動は同じ。テスト16件は通る）→ **60件**。
4. ツールが触れない箇所（定数、`Field`、ステータスコード、商品マスタ）は、**手で9通り壊して**確かめた。

## 結果

| 方法 | 件数 | 検出（killed） | 生存（survived） |
| --- | --- | --- | --- |
| 本体のまま mutmut | 5 | 3 | 2 |
| 測定用コピーで mutmut | 60 | 44（73%） | 16 |
| 手動の mutant（定数・Field・ステータス） | 9 | 7 | 2 |

### 生存した mutant の分類（mutmut の16件 + 手動の2件）

| # | 何を壊して通ったか | 件数 | 判定 |
| --- | --- | --- | --- |
| A | エラーの `code` / `message` の中身を変える（`None`、大文字、文字化け） | mutmut 14 + 手動1（検証エラーの code） | **仕様の穴。** テストは `error` の中のキー名しか確かめていない（Q8 の回答どおり）。code の値が契約かどうかは、仕様に書いていない |
| B | カートIDを `None` に置き換える（全カートが同じ箱になる） | 1 | **テストの穴。** テストは1つのカート（c1）しか使っていない。カートが互いに独立していることを、誰も確かめていない |
| C | 合算の上限 `>` を `>=` にする | 1 | **テストの穴。** 合算は 50+50=100 しか試していない。98+1=99（ちょうど上限）が通ることを確かめていない |
| D | 商品マスタから `p3` を消す | 手動1 | **テストの穴。** 仕様は p1〜p3 なのに、テストは p1、p2 しか使っていない |

- A のうち `message`（人間向けの文章）は、値を固定する必要が薄い。`code`（機械が読む識別子）は契約にするか、人間が決める必要がある。
- 等価 mutant（挙動が変わらず、落ちなくて当然のもの）は見つからなかった。

## 発見の意味
- **B と C は、TDD の「1件ずつ」では拾えなかった。** test-plan の観点（V-02、S-02）は満たしていたが、「状態の独立」（複数カート）と「境界 × 合算」の組み合わせは、カタログに無かった。観点カタログへの追加候補: **S-04 別の対象が互いに影響しない（2つのカート、2人のユーザー）**。
- **A は、Q8 の回答（形だけを固定）の副作用。** 形を確かめるテストは、値が壊れても通る。
- **構造の示唆:** ロジックを `create_app()` の入れ子に置くと、mutation testing に限らず、単体で呼べずテストしにくい。ロジックはモジュール直下の関数に置き、FastAPI のハンドラは薄くする構造のほうが、測れるし、テストもしやすい。

## 判断
| 項目 | 判断 |
| --- | --- |
| 常設（`make check` に入れる） | **しない。** 構造が合わないと5件しか測れず、数字が意味を持たない。スコアを見て安心する危険のほうが大きい |
| `make mutate`（手動） | **用意する。** 機能が done になったあとに1回回し、生存を見る使い方 |
| 次にやること | 下の提案。どれも `src/`（挙動・テスト）に触れるので、**人間が決めて、req / `/req-fb` で進める** |
| ツールの再評価 | 入れ子の関数やクロージャを使い続けるなら、全 AST を対象にできる別ツール（cosmic-ray など）も比べる |

## 提案（AI は実行しない。人間が選ぶ）
1. **テストを足す（0001 への FB）:** B（2つのカートが独立）、C（98+1=99 は通る）、D（p3 を追加できる）。期待値はいずれも既存の仕様から一意に決まるが、例は人間が書く。
2. **`code` を契約にするか決める:** するなら、`product_not_found` / `quantity_exceeded` / `invalid_request` の値をテストで固定する。しないなら、A は「許容する穴」として記録する。
3. **`src/` の構造:** ロジックを関数に切り出す（挙動を変えないリファクタリング。テストが守ってくれる）。
4. **観点カタログに S-04 を追加する**（`_catalog/` は人間が編集を指示したときだけ）。

## 再現方法
```
uv run mutmut run            # 本体。5件しか出ない（構造の制約）
uv run mutmut results --all true
uv run mutmut show <mutant名>
```
測定用コピーは、上記2の切り出しを施した複製で、本体には入れていない（`mutants/` は `.gitignore`）。
