## 一言
**カートAPI は、開発プロセスを試すための、ただの実験台。成果物は「開発プロセス」である。そのプロセスは、形にはなったが、「確立した（検証済みで、軽くて、使える）」とは、まだ言えない。**
目的は「TDD × スペック駆動 × AI駆動の、軽量な開発フローを確立すること」だった。実際にできたのは、3つの skill、`specs/` の様式、hook、CI という、**重い仕組み**。しかも、**実験台でプロセスを検証した回数は、実質 0001 の1機能だけ**で、そのあとは、プロセス自身（hook、CI）の改良に、時間を使った。

## 所感への応答

### 1. 適当に進めていて、全体像を見失った
- その通り。**途中で「ここまでで十分か」を問う地点が、一度も無かった。** 各 req は、前の req の「次の候補」から生まれた（hook → hook の誤検出 → hook の実験 → hook の分割 → 純粋関数 → CI）。1つ1つは筋が通っていたが、積み上がった先は、最初の目的とは別の物だった。
- AI 側の責任: 私は、毎回「次の候補」を出し、人間が選んだ。**「これは脇道では」と私が止めたことは、一度も無い。** 全体の地図（目的、いま何%、残り）を、定期的に出すべきだった。

### 2. TDD × SDD × AI駆動から、脇道にそれた
- 脇道の中心は **0004〜0013（hook とその周辺）**。きっかけは、0001 の実装中に「AI がテストを書き換えうる」と気づいたこと。これ自体は正しい問題意識で、0007（既存テストの書き換えを止める hook）は、実際に動いた（実環境で、書き換え・`git reset --hard` などが止まるのを確認した）。
- ただし、そのあとの 0008（監査エージェントの実験）、0009（sandbox）、0011〜0012（guard の分割、純粋関数）、0013（CI の比較）は、「hook が破られうるから、もう一層」という、**層を足し続ける連鎖**だった。**実験台（カート API）に、プロセスを2回目に適用した機会は、一度も無かった。** 0004〜0013 も、プロセスで進めたので、データは増えたが、それは「プロセス自身の改良」の記録で、**軽さを測る実験ではない**（毎回、道具の都合で、重くなる）。
- 設計見直しの案（最初に承認された表）には、「sandbox が動けば Bash 解析を削除する」という出口があった。sandbox が動かなかったので、出口が閉じ、層だけが増えた。

### 3. コミット粒度が細かすぎて、嵩増しに見える
- 事実: 286コミットのうち、0013 が86。**テスト1件ごとに「Red のコミット」と「Green のコミット」を分け、さらに `status.md` の `red`/`green` の書き換えを、毎回同じコミットに混ぜた。** 「網」のテスト（Red が無いもの）にも、コミットを作った。lint や docstring の幅の直しだけのコミットもある。
- 経緯: 初期に人間が「コミットは細かく」と指示した。私は、それを「**1テスト = 2コミット**」と解釈し、見直さなかった。人間の意図は、おそらく「戻れる単位で」だったが、確かめなかった。
- 評価: Red と Green を分ける意味は、「Red を確認した」という記録にある。しかし、その記録は、コミットメッセージの自己申告で、機械では検証していない。つまり、**粒度のコストに見合う証拠になっていない。**

### 4. 開発が遅すぎる（0013 は47分）
- 0013 の中身: 86コミット、新しいテスト52件、約1000行（src 397 + tests + workflow など）。
- 時間の使われ方（**推定**）: テスト1件ごとに `make test`（全311+件。約20〜28秒）を、Red と Green で回した。回数は約70回で、**約27分は、無関係な hook のテストの待ち時間**だった。残りは、コミット、`status.md` の書き換え、確認。
- 手戻り（AI のミス。時間を食った）:
  - lint が通らないまま、コミットした（`;` で `&&` ではなく繋いで、失敗を無視した。3回）。docstring の全角幅（E501）で、3回やり直した。
  - pyright の `extraPaths` を足して、typecheck を壊した（`src` の自動検出が消える）。
  - **`git stash` と `git checkout main -- guard.py` を、誤って実行した**（0011 の確認中。すぐ戻したが、`git config user.email` を、複製の失敗で、本物のリポジトリに書いた件もある）。
  - 「Red のテスト」の lint を、コミットの前に確かめなかった。そのため、人間に `ALLOW_TEST_CHANGE` を頼む羽目になった。
  - **GitHub 上で初めて、`| tee` が終了コードを隠すバグ（compare が緑になる）を見つけた。** 文面を見るテストでは、見つからなかった。
- 仕組みが遅さを生んだ構造: 「1件ずつ」「全件実行」「状態を毎回書く」「毎回コミット」という、**儀式が、1サイクルごとに乗る設計**。

### 5. TDD が本当に機能していたか疑わしい
疑いは、一部当たっている。事実を分けて書く。

**機能していたもの**
- 既存のテストを黙って書き換えさせない hook（0007）。実際に何度も止まった（lint の import の並びを直すときも、人間のスイッチが要った）。**「テストコードの書き換えに審査ゲートがあってよかった」という所感は、この仕組みが働いた結果。**
- mutation testing（0001で1回）は、テストの穴（カートの独立、合算の境界）を実際に見つけ、FB になった。73%→88%。
- 監査エージェントの実験（0008）は、hook が止められない4件（Makefile、仕様に対応するテストが無い、Red の記録が無い、中身の無いテスト）を、全部見つけた。

**機能していなかった、または疑わしいもの**
- **「テスト → 実装 → テスト → 実装」が、同じ AI、同じセッションで、交互に行われた。** 期待値の例は、人間が決めた選択肢（`discussion-log.md`）から来ているが、**個々のテストケースの具体例（入力と期待値）は、AI が書いた。** つまり、「期待値の出所は人間の例だけ」というルールは、0013 では、「人間が選んだ方針を、AI がテストに展開した」に弱まっていた。
- **Red の多くは、作られたもの。** 「スタブで、わざと誤った値を返す」ことで、`AssertionError` を作った（14回）。これは、「実装が無い状態で、テストが落ちる」ではなく、「落ちるように、先に、偽の実装を書いた」。ImportError を避けるための規則だったが、**Red の証拠価値は、薄い。**
- **Green が、最小ではないことがあった。** 例: 承認ラベルの対応表を、`guard` の分まで先に入れた。ワークフロー全体を、一度に書いた。そのあとの「テスト」は、Red が無い「網」になった（22コミット）。
- **新しく足すテストには、審査が無い。** hook が守るのは、「既存のテストの書き換え」だけ。新しいテストが意味のあるものか（B4: 自己比較のテストなど）は、誰も見ていない。0013 のテストの中身は、AI が書き、AI が通した。
- **テストが通っても、正しいとは限らなかった。** workflow の構造テストは、文面を正規表現で見るだけで、終了コードのバグを通した。

### 6. 仕様を人間が決めると記入欄が多くてつらい。AI に任せると承認マシーンになる
- **数字がそれを示している。** 43問のうち、選択式の回答41件の**95%が、AI の推奨と同じ**。人間は、質問を読んで、推奨に丸を付ける作業を、40回やった。
- ただし、**価値があったのは、条件や補足を足した21件。** 例: 「ツール自身の失敗は、承認があっても赤」「ラベルの有無は、イベントの写しでなく、実行時に API で読み直す」「新コミット直後にラベルが残っても、緑にならない」。これらは、AI が思いつかなかった、または、推奨に入れなかった、**人間の側の、狙いどころ**。
- つまり、「全部の質問に答える」のが無駄で、**「人間にしか出せない条件を足す」ところだけが価値**だった。質問の形式が、後者を引き出すより、前者（推奨への丸）を促していた。
- `[人]` と `[案→承認]` の出典タグを付けて、記録は残したが、**承認が実質、形式になる構造**は、変わっていない。

## 何が、うまくいったか（残すもの）
1. **既存テストの書き換えを止める hook（0007）**。実環境で働く。ゲートとして、意味がある。
2. **実環境の検査を、実際に動かして確かめること。** 0013 の GitHub 上の確認で、緑のバグが見つかった。文面のテストで満足しなかったのが、効いた。
3. **「測る」実験**: mutation（1回）、監査エージェント（1回）。どちらも、1回だけ、結果を記録して、止めた。常設しなかったのが良かった。
4. **失敗を、記録に残すこと**（`docs/experiments/`、`status.md` の気づき）。今回の振り返りも、その材料で書けた。
5. **段階を分け、挙動を変えない移動（0011）と、変える変更を、分けたこと。** 1753入力で同一性を確かめた方法は、安全だった。

## 提案（次にやること、やめること）

### 先に決める: このフローを、どう使うか
このリポジトリの目的は「**開発プロセスの確立**」。今回は、プロセスの**重さと穴**について、十分なデータが出た（上の数字）。ここで、**道具の増築を凍結**して、**実験台（カート API）に、2つ目の機能を足す、という題材で、軽くしたプロセスを、1回通す**のが、次の実験として、筋が良い。**機能が目的ではなく、プロセスの測定が目的**。測るもの: **人間の時間、経過時間、コミット数、質問数、手戻り**（今回の数字と比べる）。

### やめる（軽くする）
- **1テスト = 2コミット**をやめる。コミットは、**AC（受け入れ条件）1つにつき1コミット**。Red の記録は、コミットメッセージでなく、**`status.md` に1行（Red のログの要約）**。
- **`status.md` の `red`/`green` の毎回の書き換え**をやめる。`planned` → `done` の2点だけ。
- **テスト1件ごとの全件実行**をやめる。開発中は**対象のテストだけ**（`pytest -k`）。全件は、AC の区切りと、コミット前に1回。
- **S2 の全行評価（カタログ14行）**を、標準にしない。S2 は、リスクタグのあるものだけ。
- **質問の「全問に答える」形式**をやめる（下）。
- **「網」のためのコミット**を、独立させない（その AC のコミットに含める）。

### 続ける
- 既存テストの書き換えを止める hook（0007）と、`origin/main` との比較（0013）。この2つは、**セットで**、最小の守り。
- 実環境での確認（CI を実際に動かす）。
- 実験は「1回だけ、記録して、止める」。

### TDD を、本当に機能させる（案）
1. **テストを書く者と、実装する者を、分ける。** テストは、仕様（人間の例）だけを見る subagent が書き、実装は、テストだけを見る側が書く。**同じ頭の中で、期待値と実装が、すり合わないようにする。**
2. **Red は、スタブを書かずに作る。** 実装が無い（`NotImplementedError` を投げる骨組みだけ）状態で、**例外でなく、assertion で落ちる**ように、テスト側を書く（戻り値の型だけの骨組みを、テストの側の責任にする）。難しければ、「Red の記録」を、緩める（実装が無く、テストが落ちることだけを要求する）。
3. **新しく足すテストの審査**: green になる直前に、**監査役（読み取り専用、助言のみ）を1回**走らせる（0008 で、11/11）。常設は、助言だけ。
4. **mutation testing** を、S1以上の req の完了時に、1回。点数でなく、「見逃した穴」を、FB にする。

### 仕様の負担を、構造で減らす（案）
- 決定を2種類に分ける。
  - **人間が決める（少数）**: 取り返しがつかないこと、セキュリティ、お金・個人情報・認証・データ削除、**仕様の「してはいけないこと」**、期待値の**具体例**（入力と出力）。1 req あたり**最大3問**。
  - **AI が決めて、記録する（多数）**: 実装の選択、名前、構造、細かい仕様の穴の埋め方。**人間は、事後に、サンプルで確認する**（週に1回、AI が決めたことを5件、抜き打ちで見る）。
- 質問は、「A/B どちらがよいか」でなく、「**次の条件を、1つ足すとしたら何か**」（人間にしか出せない狙いどころ）を、**空欄で聞く**。推奨は出さない（出すと、丸を付ける作業になる）。今回、価値があった21件は、全部、この形だった。
- 人間が書くのは、**具体例だけ**（入力 → 期待）。AI は、それをテストにする。

### 速度の目標（案）
- 1 req（S1）あたり、**人間の拘束時間 15分以内、経過時間 30分以内、コミット 10以内**。超えたら、そこで止めて、原因を `status.md` に書く。

## 決めてほしいこと
1. **次の実験の設計**: プロセスの確立のために、次に何を測るか。（私の推奨: 道具を凍結して、実験台（カート API）に、題材として2つ目の機能を足し、軽量版のフローを1回測る）
2. **残りの別 req**（`gh` の導入と `permissions`、段階4、CLAUDE.md への反映）を、やるか、凍結するか。（私の推奨: `permissions` の設定（`--label` の deny など）だけは、承認ラベルの安全性に必要なので、小さくやる。残りは、凍結）
3. **コミットの粒度の決まり**（AC 単位）を、`CLAUDE.md` と `/req-run` に反映するか（要 UNLOCK）。
4. **質問の形式の見直し**（最大3問、推奨を出さない、空欄で聞く）を、`/req-new`・`/req-run` に反映するか。
