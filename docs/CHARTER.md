# 個人ラボ企画書：TDD x SDD x Skills x 開発環境

## 背景と課題

AIでコードとテストを速く作れるようになった今、ボトルネックは「信頼」と「レビューの手間」に移っています。

- AIが書いたコードとAIが書いたテストは、同じ勘違いを共有しやすく、テストが通っても安心できません
- 人間が全PRを読む運用は、AIの生産速度に追いつかず、疲れて雑になります
- 新しいプロジェクトのたびに環境を作るのが面倒で、実験の始まりが遅くなります
- devcontainerに移ると、これまでのClaude Code履歴が見えなくなり、過去の知見を使いにくくなります

## ゴールと成果物

ゴールは、AIと速く、かつ安全に作れる「自分用の型」を持つことです。成果物は次の4つです。

1. 開発リポジトリの土台：Python（uv、pytest、ruff、pyright、hypothesis）、devcontainer、CLAUDE.md、test-reviewer。当面はこのリポジトリ自体を土台にし、テンプレート化は型が固まってから行います
2. 開発の型：仕様を先に書くSDDと、テストを先に書くTDDを融合した軽いフロー（`specs/`）と、AIへの指示
3. Skills：`/req-new`、`/req-run`、`/req-fb` など、繰り返す作業の再利用部品（カスタムコマンドはSkillsに統合済みのため、同じ仕組みで作る）
4. PR運用：ブランチ保護、CODEOWNERS、AIレビュー、docs系の自動マージ

## 全体像

人間は「何を作るか」と「具体的な期待値の例」だけを決め、書く作業はAI、確認は機械に任せる構成です。柱は3本です。

| 柱 | 中身 | 役割 |
| --- | --- | --- |
| 開発の型 | 要望(req)、質問、test-plan、テスト、実装の順。サイズはS0/S1/S2の3段階 | 人間が例を出して選び、AIが書く |
| Skills | `/req-new`、`/req-run`、`/req-fb` など | 型を毎回書かずに呼び出せる |
| 環境 | devcontainer、uv、履歴の引き継ぎ | 始めるまでの手間をなくす |

この3本を支える「壁」は、人間のレビューではなく機械のルールで作ります。.github、CLAUDE.md、.claudeの変更は人間の承認を必須にして、AIが自分でルールを書き換えられないようにします。ただしPRの壁（M2）は後回しのため、それまでは規約（`specs/README.md`）で運用し、hook段階で `.claude/**` などへの編集拒否を足します。リリースの認証情報はPR側に置かず、別ワークフローに分けます。

## スコープ

今回はPR周りと開発環境に絞り、リリース系は含めません。Pythonを先に作り、TypeScript版は必要になってから考えます。

**やること**

- devcontainer内でClaude Codeの履歴を見られるようにする（M0、完了済み）
- Python向けの開発環境と、TDD、SDDの軽いフローの整備
- Skillsの作成
- PRの壁（ブランチ保護、CI必須、CODEOWNERS）と、AIレビューの自動化（後回し）

**やらないこと**

- AWSなどへのリリース（別ワークフローとして、あとで作る）
- 外部の人からのPRへの対応（内輪での利用が前提）
- 監査用の記録、重い承認プロセス、大きな仕様書
- 最初から全部作り込むこと

## マイルストーン

まず履歴の引き継ぎ(M0)を片付け、実際にフローを回して(M3)、部品化(M4)してから、テンプレートと壁(M1、M2)を固めます。期日は未定です。「やってみて困ってから足す」順です。

1. M0：devcontainerで過去のClaude Code履歴を見られるようにする（完了）
2. M3：カートAPI（Python、FastAPI）でSDDとTDDを実際に回し、速さと信頼を確かめる。最初のお題は「商品を追加する」（S1、リスクタグなし）
3. M4：Skills化（`/req-new`、`/req-run`、`/req-fb`）、TDD規律のhook、ghとClaude CLIによるAIレビュー、docs系の自動マージ
4. M1：テンプレートリポジトリ化（M3、M4で固まった型を切り出す。言語はPython、TypeScript版は必要になってから）
5. M2：PRの壁（ブランチ保護、CI必須、CODEOWNERS）
6. M5以降：mutation testing（まず1機能に1回だけの実験）、差分カバレッジ、依存変更の人間チェック、リリース用の別ワークフロー

番号は当初の呼び名のままにしています。進める順序は M0 → M3 → M4 → M1 → M2 です。

## リスク、成功の見方、次の一歩

最大のリスクは、作り込みすぎて進まなくなることです。1マイルストーンずつ進め、困ってから足します。

| リスク | 対策 |
| --- | --- |
| AIが通すための小細工をする | テストの期待値は人間の例から取る。実装からの逆算をしない。実装フェーズはtests/を触らない（hookで機械化、M4）。test-reviewerで別の目を入れる |
| ~/.claudeの共有で認証情報が漏れる | イメージに焼き込まない。コンテナの権限を絞る |
| 自動マージで壊れる | docs/** だけを許可する（許可リスト）。CI必須にする。すぐ戻せる状態を保つ |
| M2が後回しのため、ルールファイルをAIが書き換えられる | M4のhookで .claude/** と CLAUDE.md などの編集を拒否する（2026-10-01 に拒否を確認）。Bash は書き込みに見えるコマンドだけを見るベストエフォートなので、完全な防御は M2（ブランチ保護、CODEOWNERS）まで待つ |
| フローが重くなり、使わなくなる | サイズを3段階に分け、S0は受け入れ条件からテストへ直行。重いものは足さない |

**成功の見方**

- コンテナ内で、過去のClaude Code履歴を見られる
- カートAPIの1機能をTDDで回し、人間がやったのは「具体例を出す」と「選ぶ」だけで済んだ
- docs系のPRが、人手を介さずマージされる
