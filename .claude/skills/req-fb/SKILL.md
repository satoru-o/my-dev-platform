人間のFBに対応する。引数: `$ARGUMENTS`（NNNN。例 `0001`）。
ルールの正本は `specs/README.md`。`/req-run` と同じ約束（期待値の出所は人間の例だけ、`tests/` は実装フェーズで触らない、など）に従う。

## 0. 準備
1. `specs/$ARGUMENTS-*/` の `status.md`、`req.md`、`discussion-log.md`、`test-plan.md`（あれば）を読む。無ければ止まる。
2. **未対応のFBを探す**: `discussion-log.md` の `## FB n` のうち、直後に `### AI回答（FB n）` が無いもの。
   - 1件も無ければ「未対応のFBはありません」と伝えて止まる（何も変更しない）。
3. **既存テストを全部実行する**: `make test`。テストが0件ならスキップしてそう報告する。失敗があれば、そこで止まって報告する。直さない。

## 1. FBごとに分類して、一行で伝える
未対応のFBを古い順に1件ずつ、次のどれかに分類し、「FB n は〇〇として扱います。理由は〜」と一行で伝える。迷ったら挙動の変更に寄せる。

| 種類 | 例 | 動き |
| --- | --- | --- |
| 承認・感想・方針のみ | 「この方針でよい」「ここが良かった」 | 変更なし。AI回答だけ書く |
| 保護対象の変更依頼 | `CLAUDE.md`、`.claude/**`、`.github/**`、`specs/README.md`、`specs/_catalog/**` | 人間が編集を明示していれば編集する。そうでなければ提案だけにする |
| 挙動の変更（機能の追加・変更） | 「99個を10個までにして」 | 下の「2. 挙動の変更」へ |
| バグ報告 | 「この入力で500になる」 | 下の「3. バグ」へ |
| chore | 依存、道具、ドキュメント、整形 | 確認コマンドを先に宣言してから直す。req（ACやテスト）は変えない |

1件のFBに複数の依頼が混ざっていたら、依頼ごとに分けて分類する。

## 2. 挙動の変更
1. **期待値は、FBに書かれた人間の例だけから取る**。例が無い・足りないときは、`discussion-log.md` に新しいRoundを積み、質問（シナリオ + 選択肢 + 推奨 + 推奨の理由）を書いて `status: clarifying` にして止まる。AIが期待値を作らない。
2. `req.md` の受け入れ条件・制約を、差分だけ更新する（FBに由来する旨が分かるように、制約には「（FB n）」を付ける）。
3. **既存テストの変更が必要なら、勝手に直さない**。影響するテスト名と、どう変わるかを `discussion-log.md` の新しいRoundに質問として書いて止まる（推奨つき）。承認後に変更する。
4. S1以上は `test-plan.md` の該当行だけを更新・追加する。「適用しない」の理由や `⚠️` の行が増えたら、G2として人間に見せて止まる。変わらなければ止まらない。
5. `status: planned` にし、`/req-run` の「planned → red → green」と同じ規律で、**差分のテストだけ**を1件ずつ Red → Green → Refactor で進める。Redは assertion での失敗のみ。テストは `ruff format` を済ませてから実行する。実装フェーズでは `tests/` に触らない。

## 3. バグ
1. **直す前に、再現テストを足す**（Red。assertion での失敗）。期待値は、FBに書かれた人間の例から取る。無ければ質問にする。
2. 最小の実装で Green にする。`tests/` は触らない。
3. バグの種類が観点カタログに無ければ、`_catalog/viewpoints.md` への追加を**提案する**（AI回答に書く）。編集は人間の指示があったときだけ。

## 4. 仕上げ
1. 変更があったら `make check` を実行する。失敗があれば止まって報告する。
2. **AI回答を書く**（FBごと）: 該当FBの直後に `### AI回答（FB n）` を書く。内容は「対応した内容」「変更したファイル・コミット」「提案にとどめたこと」「直さなかったことと理由」。`discussion-log.md` に追記するときは、直前の内容との間に必ず空行を1行入れる。人間が書いた末尾に改行が無いことがあるので、追記前に末尾の改行を確認し、足りなければ改行を足してから書く。
3. `status.md` の「結果」に、FB nで何が変わったかを1〜2行で足す。`status` は、コードを変えたなら `green`、変えていなければ元のまま。「いま」を更新する（例: 「FB 1 に対応。G3で確認してください」）。
4. 挙動を変えたときは、**G3（done）で止まる**。`done` にするのは人間の確認後（FBで一度 done を外れたものは、再度 G3 が要る）。

## 共通の約束
- コミットは細かく分ける（テスト、実装、ドキュメントを別々に）。pushはしない。
- 止まるときは、何が必要か（質問・承認・失敗の内容）を1〜3行で伝え、次に打つコマンド（例 `/req-fb 0001`、`/req-run 0001`）を示す。
- 保護対象のファイルは、人間が明示的に編集を指示していない限り、提案だけにする。
- チャットの説明は要約にして、正本は `discussion-log.md` に置く。
