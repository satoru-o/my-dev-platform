### AC-1 書き込み先が保護対象でなければ、通す

| --- | --- | --- |
| heredoc に書き込み関数（`open(p,'w')`）と、保護パス（`.claude/…`）という文章がある。書き込み先は `specs/` | 通る | [案→承認] |
| 保護パスがコマンドの文章だけにある（書き込みなし）。例: `git commit -m "docs: CLAUDE.mdを更新"`、`echo` で `.claude/hooks` という文字列を表示するだけ | 通る | [案→承認] |

## やらないこと
（暫定・要確認）
- 保護の範囲（対象パスの一覧）の変更
- Bash の判定を「完全な防御」にすること。ベストエフォートという位置づけは変えない
- 書き込み先が見えないもの（例: `p=sys.argv[1]` のあと `open(p,'w')`）は、今回は今までどおり通す。見逃しは残る。拒否に変える案は、別の要望で検討する（Q1=B）
- 書き込みとみなす python の関数の範囲を広げること（`os.system`、`subprocess` など）。別の要望で検討する（Q3=A）
- Write / Edit / NotebookEdit の判定の変更

## 制約
（暫定・要確認）
- 編集対象は `.claude/hooks/guard.py` と `.claude/hooks/test_guard.py` だけ（と `specs/0004-*`）
- 既存のテスト87件は変更せず、全件通す（特に、拒否側の期待は変えない）。拒否すべきものが通る退行を作らない
- 保護対象の編集には UNLOCK（`.claude/UNLOCK`）が要る。人間が置き、編集後に外す
- テストを先に足し（Red）、そのあと guard.py を直す（Green）。guard.py の修正中は、`test_guard.py` に触らない
- heredoc の本文は、受け取るコマンドで扱いを分ける。判定できないコマンドは、実行されるものとして扱う（Q2=A）
- （Round 2 回答）引用符なしの heredoc の本文の `$(…)` とバッククォートは、中身を調べる。引用符あり（`<<'EOF'`、`<<"EOF"`）は調べない。**解析しきれないものは、拒否側に倒す**（Q4=A）
- （Round 2 回答）heredoc が終わったあとの行は、普通のコマンドとして調べる（Q5=A）
- （Round 2 回答）巨大な入力でも、判定が遅くならない。しきい値は、マシンの速さでぶれにくいよう、タイムアウト（10秒）の数分の1とする。入力は、無害な大きな本文と、最悪ケース（閉じていない heredoc、繰り返しの多い本文）の2種類（Q6=A。しきい値は Q8）
- （Round 3 回答）速さのしきい値は、無害な1MBの本文と、最悪ケース（閉じていない heredoc、繰り返しの多い本文）の、どちらも**2秒以内**（hook のタイムアウト10秒の1/5）（Q8=A）
- （FB 1）heredoc の書き方のゆれ（`<<-'EOF'`、`<<\EOF`、here-string、`EOF` に似た行）でも、本文のあとのコマンドを見逃さない。具体例は Q7 で承認され、AC-1 と AC-2 に足した
