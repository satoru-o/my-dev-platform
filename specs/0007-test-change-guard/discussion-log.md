## Round 1

### Q1. 人間が「テストの変更を承認する」とき、hook にどう伝える？
- シナリオ: 既存テストの期待値を、本当に変えたい。人間が「変えてよい」と承認したことを、hook に知らせる方法が要る。
- 選択肢:
  - A. `.claude/UNLOCK` を流用する（UNLOCK がある間は、既存テストの変更も通る）
  - B. テスト専用のスイッチを作る（例: `.claude/ALLOW_TEST_CHANGE`。人間が `! touch` で置き、編集後に外す。UNLOCK とは別）
  - C. req の中に承認を書く（`status.md` に「テスト変更を承認」と書く）
- 推奨: B
- 推奨の理由: UNLOCK は「ルールや設定の編集」の承認、こちらは「期待値（仕様）の変更」の承認で、意味が違う。A だと、`guard.py` の修正のために UNLOCK を置いたとき、意図せず、テストの書き換えも通ってしまう。C は、AI も `status.md` を書けるので、人間の承認にならない。
- 回答: B。ただし、(a) AIがBashでスイッチを作るのは拒否、(b) 1回使ったら自動で消える

### Q2. 「既存のテスト」の基準は、どこ？
- シナリオ: Red のテストを書いた。コミットする前に、typo に気づいて直したい（同じ作業の中）。
- 選択肢:
  - A. ディスク上の、今の内容を基準にする（今書いたテストを直すのも「変更」。コミット前でも拒否）
  - B. 最後にコミットした内容（git の `HEAD`）を基準にする（未コミットのテストは、直すのも自由。コミットしたら「既存」になる）
- 推奨: B
- 推奨の理由: Red を確認してコミットした時点が、「期待値を決めた」境界になる。それまでは検証前なので、自由に直せる。コミットしたあとは、実装中に黙って変えられない。A は、Red の確認前の typo でも、毎回承認が要り、重い。B の弱点は、「コミットせずに、実装に合わせて直す」とすり抜けられること。ただし、Red を実装の前に確かめてコミットする規則（`/req-run`）を守れば、すり抜けにならない。
- 回答: B。ただし、amend / reset / rebase / checkout -- / restore も、Q3の拒否に含める

### Q3. Bash 経由の書き換えは、どうする？
- シナリオ: `sed -i 's/201/200/' tests/test_add_item.py` や、`cat >> tests/test_add_item.py`、python の `open(…,'w')` で、テストを書き換える。Bash は中身を解析できない（今の判定は、コマンドの文字列を見るだけ）。
- 選択肢:
  - A. 既存のテストファイルへの Bash 経由の書き込みは、**すべて拒否**（`sed -i`、`>`、`>>`、`mv`、`rm`、python の書き込み）。まだ無いファイルへの書き込みは通す。追記は、Edit ツールを使う
  - B. `>>`（末尾への追記）だけ通し、それ以外の、既存ファイルへの書き込みは拒否
  - C. 判定しない（今までどおり。Bash 経由の書き換えは、抜け道として残る）
- 推奨: A
- 推奨の理由: `>>` で末尾に `pytestmark = pytest.mark.skip` を足すと、全テストを無効にできる（B の穴）。追記は Edit で足りる（Edit は、中身を解析できる）。C は、AC-2 の拒否を、Bash で回避できてしまう。
- 回答: A。hookは1枚目。最終防衛は、コミット時のHEADとのAST比較（別のreqで）

### Q4. 新しく足すテストに、skip や xfail が入っていたら？
- シナリオ: 新しいテスト関数を足す Edit の中に、`@pytest.mark.skip` や `@pytest.mark.xfail` がある。ファイル全体を無効にする `pytestmark = pytest.mark.skip` も同じ。
- 選択肢:
  - A. 拒否する（skip / xfail を足す変更は、新しいテストでも、承認が要る）
  - B. 通す（新しいテストなので、足すのは自由）
- 推奨: A
- 推奨の理由: skip / xfail は、「通らないものを、通ったことにする」ための道具。足す場面は少なく、承認の手間も小さい。B だと、新しいテストの形で、実質的に弱められる。
- 回答: A。pytestの設定ファイル（addopts、collect_ignore）の変更も、承認が要る

### Q5. どのファイルを守る？
- シナリオ: `tests/` の下には、`test_*.py` のほかに、`conftest.py`（fixture）や補助のモジュール、データのファイルがある。fixture を変えるだけでも、テストを弱められる。
- 選択肢:
  - A. 既存の Python ファイルすべて（`test_*.py`、`conftest.py`、補助モジュール）。Python 以外（データ）は、対象外
  - B. `test_*.py` だけ
  - C. `tests/` の下の既存のファイルすべて（Python 以外も、変更を一律に拒否）
- 推奨: A
- 推奨の理由: B は、`conftest.py` の変更で回避できる。C は、データファイルの正当な更新まで止まり、重い。
- 回答: A。ただし、期待値を持つデータ（`req.md` など）も対象に含める

### Q6. スイッチの「1回」は、何の単位？ AI のスイッチ作成は、どこまで拒否する？
- シナリオ: Q1 で、「AI が Bash でスイッチを作るのは拒否」「1回使ったら自動で消える」が条件になった。
- 案:
  - (a) `.claude/ALLOW_TEST_CHANGE` を作る・触る操作（Write、Edit、Bash の `touch`、`>`、`cp`、`mv`、`ln`）は、AI からは、UNLOCK があっても、常に拒否。人間が、`!` で置くだけ
  - (b) 「1回」は、ツール呼び出し1回（Edit 1回、Write 1回、Bash 1回）。スイッチがある状態で、守る対象への変更が通ったら、hook がスイッチを消す。通したあとで、その呼び出しが失敗しても、スイッチは消えたまま（安全側）

  - B. (a) のとおり。(b) は、「同じファイルへの変更が続くあいだ」は通し、別のファイルに触れたら消す

### Q7. git の履歴や、ファイルを戻す操作は、どこまで拒否する？
- シナリオ: Q2 で、基準を `HEAD` にした。次の操作は、`HEAD` や、テストの中身を、変えてしまえる。いつも使う、無害な操作（`git add`、`git commit`、`git checkout <ブランチ>`、`git reset`（引数なし。`add` の取り消し）、`git status`、`git diff`）は、止めたくない。
  - 履歴を動かす・書き換える: `git commit --amend`、`git rebase`、`git reset --hard`、`git reset --soft|--mixed <コミット>`
  - ファイルを別の内容に戻す: `git checkout <ref> -- <パス>`、`git restore <パス>`、`git restore --source=<ref>`
- 選択肢:
  - A. 上の、履歴を動かす操作は**常に拒否**。ファイルを戻す操作は、**守る対象のパス**（`tests/`、pytest の設定、`req.md` など）に触れるときだけ拒否
  - B. 上のすべてを、**常に拒否**（パスにかかわらず）
  - C. 履歴を動かす操作だけ拒否。ファイルを戻す操作は、`HEAD` の内容に戻すだけなので、通す
- 推奨: A
- 推奨の理由: 履歴を動かす操作は、どこで使われても `HEAD` の意味が変わるので、常に止める。ファイルを戻す操作は、守る対象以外では、普通に使う。C は、`git checkout <古いコミット> -- tests/` で、古いテストに差し替えられる（`HEAD` を基準にしても、すり抜ける）。

### Q8. pytest の設定は、どこまで承認が要る？
- シナリオ: Q4 で、「`addopts`、`collect_ignore` など、pytest の設定の変更も承認が要る」という条件が付いた。AI の案の例:
  1. `pyproject.toml` の `[tool.pytest.ini_options]` の `addopts` に、`-k "not slow"` を足す（一部のテストを外す）→ 拒否

  3. `pyproject.toml` の `[tool.ruff]` を変える → 通す（pytest の設定ではない）
  4. `[tool.pytest.ini_options]` の `testpaths` を変える（減らす）→ 拒否
  5. `[tool.pytest.ini_options]` に、新しい `markers` の行を足す → 拒否か、通すか（下の選択肢）
- 選択肢:

### Q9. `req.md` は、どの時期の、どの変更を止める？
- シナリオ: Q5 で、「期待値を持つデータ（`req.md` など）も守る」という条件が付いた。`req.md` の AC の表には、人間が承認した期待値がある。実装中に AI が書き換えると、「実装に合わせた期待値」が、仕様になってしまう。ただし、AI は、質問への回答の反映、AC の行の追加（0004 の Q9 のように）で、`req.md` を、正当に編集する。
- 案:
