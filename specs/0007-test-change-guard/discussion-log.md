## Round 1

### Q1. 人間が「テストの変更を承認する」とき、hook にどう伝える？
- シナリオ: 既存テストの期待値を、本当に変えたい。人間が「変えてよい」と承認したことを、hook に知らせる方法が要る。
- 選択肢:
  - A. `.claude/UNLOCK` を流用する（UNLOCK がある間は、既存テストの変更も通る）
  - B. テスト専用のスイッチを作る（例: `.claude/ALLOW_TEST_CHANGE`。人間が `! touch` で置き、編集後に外す。UNLOCK とは別）
  - C. req の中に承認を書く（`status.md` に「テスト変更を承認」と書く）
- 推奨: B
- 推奨の理由: UNLOCK は「ルールや設定の編集」の承認、こちらは「期待値（仕様）の変更」の承認で、意味が違う。A だと、`guard.py` の修正のために UNLOCK を置いたとき、意図せず、テストの書き換えも通ってしまう。C は、AI も `status.md` を書けるので、人間の承認にならない。

### Q2. 「既存のテスト」の基準は、どこ？
- シナリオ: Red のテストを書いた。コミットする前に、typo に気づいて直したい（同じ作業の中）。
- 選択肢:
  - A. ディスク上の、今の内容を基準にする（今書いたテストを直すのも「変更」。コミット前でも拒否）
  - B. 最後にコミットした内容（git の `HEAD`）を基準にする（未コミットのテストは、直すのも自由。コミットしたら「既存」になる）
- 推奨: B
- 推奨の理由: Red を確認してコミットした時点が、「期待値を決めた」境界になる。それまでは検証前なので、自由に直せる。コミットしたあとは、実装中に黙って変えられない。A は、Red の確認前の typo でも、毎回承認が要り、重い。B の弱点は、「コミットせずに、実装に合わせて直す」とすり抜けられること。ただし、Red を実装の前に確かめてコミットする規則（`/req-run`）を守れば、すり抜けにならない。
- 回答: 

### Q3. Bash 経由の書き換えは、どうする？
- シナリオ: `sed -i 's/201/200/' tests/test_add_item.py` や、`cat >> tests/test_add_item.py`、python の `open(…,'w')` で、テストを書き換える。Bash は中身を解析できない（今の判定は、コマンドの文字列を見るだけ）。
- 選択肢:
  - A. 既存のテストファイルへの Bash 経由の書き込みは、**すべて拒否**（`sed -i`、`>`、`>>`、`mv`、`rm`、python の書き込み）。まだ無いファイルへの書き込みは通す。追記は、Edit ツールを使う
  - B. `>>`（末尾への追記）だけ通し、それ以外の、既存ファイルへの書き込みは拒否
  - C. 判定しない（今までどおり。Bash 経由の書き換えは、抜け道として残る）
- 推奨: A
- 推奨の理由: `>>` で末尾に `pytestmark = pytest.mark.skip` を足すと、全テストを無効にできる（B の穴）。追記は Edit で足りる（Edit は、中身を解析できる）。C は、AC-2 の拒否を、Bash で回避できてしまう。

### Q4. 新しく足すテストに、skip や xfail が入っていたら？
- シナリオ: 新しいテスト関数を足す Edit の中に、`@pytest.mark.skip` や `@pytest.mark.xfail` がある。ファイル全体を無効にする `pytestmark = pytest.mark.skip` も同じ。
- 選択肢:
  - A. 拒否する（skip / xfail を足す変更は、新しいテストでも、承認が要る）
  - B. 通す（新しいテストなので、足すのは自由）
- 推奨: A
- 推奨の理由: skip / xfail は、「通らないものを、通ったことにする」ための道具。足す場面は少なく、承認の手間も小さい。B だと、新しいテストの形で、実質的に弱められる。

### Q5. どのファイルを守る？
- シナリオ: `tests/` の下には、`test_*.py` のほかに、`conftest.py`（fixture）や補助のモジュール、データのファイルがある。fixture を変えるだけでも、テストを弱められる。
- 選択肢:
  - A. 既存の Python ファイルすべて（`test_*.py`、`conftest.py`、補助モジュール）。Python 以外（データ）は、対象外
  - B. `test_*.py` だけ
  - C. `tests/` の下の既存のファイルすべて（Python 以外も、変更を一律に拒否）
- 推奨: A
- 推奨の理由: B は、`conftest.py` の変更で回避できる。C は、データファイルの正当な更新まで止まり、重い。
