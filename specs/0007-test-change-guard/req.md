## やりたいこと
既存テストを黙って書き換えさせない hook（足すのは自由、変える・弱める・消すは人間の承認）

## やらないこと
（暫定・要確認）
- コミット時に、`HEAD` とテストを AST で比べる最終防衛（hook は1枚目。最終防衛は、別の req で）（Q3）
- `git merge`、`git cherry-pick`、`git apply` による、テストの書き換え。hook では止められないので、最終防衛の別の req で拾う（Q7）
- Makefile と CI の pytest 呼び出しの扱い（Q10=A。CI の設定ファイルは、`.github/**` として、すでに UNLOCK で守られている）
- **最終防衛の別 req への引き継ぎ（Q10 の条件）**: 「収集したテスト件数が減ったら失敗」を、最終防衛の req に入れる（Makefile の `tests` を外す、`collect_ignore` で外す、などの迂回を、件数の減少として拾う）
- status が red のときの動き（今までどおり、`tests/` への書き込みは、すべて拒否）の変更
- `.claude/hooks/test_guard.py`（保護対象。UNLOCK で守られている）への適用
- テストの差分を `make check` で調べること（AST で比べる機械チェック）、監査エージェント、mutation のラチェット。別の要望で検討する
- 保護の範囲（対象パスの一覧）、`src/` の判定の変更

## 制約
（暫定・要確認）
- 編集対象は `.claude/hooks/guard.py` と `.claude/hooks/test_guard.py` だけ（と `specs/0007-*`）
- 既存の hook のテスト133件は変更せず、全件通す（特に、拒否側の期待は変えない）。拒否すべきものが通る退行を作らない
- 巨大な入力（数MBのファイルの Write など）でも、判定は2秒以内（hook のタイムアウトは10秒。超えると素通りになる）
- 保護対象の編集には UNLOCK（`.claude/UNLOCK`）が要る。人間が置き、編集後に外す
- テストを先に足し（Red）、そのあと `guard.py` を直す（Green）。`guard.py` は、作業用のコピーで確かめてから、本物に反映する
- （Round 1 回答 Q1=B）解除のスイッチは、UNLOCK とは別の、テスト専用のスイッチ（`.claude/ALLOW_TEST_CHANGE`）。人間が `! touch` で置く。条件が2つ付いた: (a) AI が Bash でスイッチを作るのは拒否（UNLOCK があっても、常に拒否）、(b) **1回使ったら、自動で消える**。「1回」の単位などの詳細は、Round 2 で決める
- （Round 1 回答 Q2=B）「既存」の基準は、最後にコミットした内容（`git` の `HEAD`）。未コミットのテストは、直すのも自由。条件が付いた: `git commit --amend`、`rebase`、`reset`、`checkout --`、`restore` も、Q3 の拒否に含める（`HEAD` の意味を変えて、テストの変更を洗い流せてしまうため）。対象の範囲は、Round 2 で決める
- （Round 1 回答 Q3=A）既存のテストファイルへの Bash 経由の書き込みは、すべて拒否（`sed -i`、`>`、`>>`、`mv`、`rm`、python の書き込み）。まだ無いファイルへの書き込みは通す。追記は Edit ツールを使う
- （Round 1 回答 Q4=A）新しく足すテストでも、skip / xfail（ファイル全体を無効にする `pytestmark` を含む）は拒否。条件が付いた: pytest の設定ファイル（`addopts`、`collect_ignore` など）の変更も、承認が要る。対象の範囲は、Round 2 で決める
- （Round 1 回答 Q5=A）守るのは、`tests/` の下の既存の Python ファイルすべて（`test_*.py`、`conftest.py`、補助モジュール）。Python 以外のデータは、原則として対象外。条件が付いた: **期待値を持つデータ（`req.md` など）も、対象に含める**。範囲は、Round 2 で決める
- （Round 2 回答 Q6=A）スイッチの「1回」は、ツール呼び出し1回。消えるのは、**守る対象への変更が通ったときだけ**（無関係な呼び出しでは消えない）。通したあとで、その呼び出しが失敗しても、消えたまま
- （Round 2 回答 Q7=A）履歴を動かす git 操作は、常に拒否。ファイルを戻す操作は、守る対象のパスに触れるときだけ拒否。パスが「全部」を指す形（`git restore .` など）は、守る対象に触れると判定する。`merge`、`cherry-pick`、`apply` は、やらないこと
- （Round 2 回答 Q8=A）pytest の設定は、足す・消す・変えるの区別なく、承認が要る。`pyproject.toml` は、`[tool.pytest.ini_options]` の節だけを、変更の前後で比べる
- （Round 2 回答 Q9=A）`req.md` は、実装中（planned / red / green）だけ、AC の表の既存の行の変更・削除を拒否。行を足すのは通す。行の同一性は、AC 番号をキーにする（番号の書き換えは、削除と追加として拒否）
- （Round 3 回答 Q10=A）Makefile の pytest 呼び出しは、今回は守らない。最終防衛の別 req に、「収集したテスト件数が減ったら失敗」を入れる（引き継ぎ）
- （Round 3 回答 Q11=A）コミットが0件なら、すべて新規として通す。`git` の失敗は拒否（安全側）。「コミット0件」と「`git` の失敗」は、別に判定し、テストも分ける。`git` は、作業フォルダを固定し、`GIT_` で始まる環境変数を掃除して呼ぶ。タイムアウトは拒否
- （Round 3 回答 Q12=A）`HEAD` にある名前の定義（関数、クラスのメソッド、代入での上書きを含む）が、`HEAD` より増えるときは拒否。別のクラスの同名のメソッドは通す
- 解析しきれないもの（構文エラーなど）は、拒否側に倒す（0004 の Q4 と同じ原則。AI の暫定。違えば指摘してください）
- AI の暫定（実装上の取り決め。違えば指摘してください）: (1) スイッチが消えるのは、スイッチがなければ拒否される変更を、スイッチが通したときだけ（元々通る変更では、消えない）。(2) 承認した変更は、`HEAD` と食い違った状態になるので、すぐコミットする（次の変更は、`HEAD` との比較になる）。(3) 内容の情報がない呼び出し（`file_path` だけ）は、内容を比べられないので、今までどおり通す（実際の Edit・Write は、必ず内容を持つ）。(4) `git` の失敗でも、ディスクに無いファイルへの Bash 経由の新規作成は、通す（既存の133件の期待と、整合させるため）。(5) `git rm`、`git mv` も、守る対象のパスには、拒否する（`rm`、`mv` と同じ）
