## やりたいこと
`origin/main` と比べて、既存のテスト・pytest の設定・Makefile などが、黙って弱められていないかを検査する仕組みを足し、CI でも、ローカル（`make`）でも動かす。設計見直しの段階3。

（人間の指示は、設計見直しの案への承認と、補足のみ。受け入れ条件は、`discussion-log.md` の Round 1 の回答（Q1〜Q5）から起こした。Round 2 の回答待ちの点は、`⚠️ 未回答`。）

## 前提（人間が決めたこと。質問しない）
- 比較の基準は `origin/main`（merge-base）。
- ブランチ保護・必須チェックは使えない（非公開の Free プラン）。赤のままマージしないのは、運用で守る。マージは人間だけ。
- 承認の正本は、CI の PR ラベル。ローカルは警告のみ。
- この req の外の前提（別の小さな req）: `settings.json` の `permissions` で、`gh pr create` の `--label` / `-l` を deny に入れる。`gh pr edit` は許可しない。`gh api` は deny。これが無い間は、承認ラベルの安全性が足りないので、この req の機能は、その設定が入ってから有効にする。

## やらないこと
（暫定・要確認）
- AC 番号の対応（仕様の項目に、対応するテストがあるか）。「テストが AC 番号を参照する約束」を入れる req が先で、そのあとの req で足す（Q5=A）
- `pull_request_target` による強化案（信頼できる側のコードで検査する）。将来のメモとして残す。今回はやらない（Q4）
- hook の変更（誤検出の緩和は、段階6）。`tool = 1` で例外になる関数そのものの修正（呼び出し側が、例外を、ツール自身の失敗として赤にする）
- sandbox、`permissions.deny` による保護（段階4）、ブランチ保護・必須チェック
- 意味を読む監査（subagent。段階7）
- `gh` の導入と認証、`settings.json` の `permissions`（別の小さな req）

## 制約
（暫定・要確認）
- 比較の基準は `origin/main`（merge-base）。AI が書き換えられない場所（リモートの `main`）に置く
- 検査の本体は、純粋関数（`guardlib/compare.py` の `change_reason_for`）を、そのまま使う。判定の複製を作らない
- `.github/**`、`.claude/**` は保護対象。人間が UNLOCK を置いてから編集する
- 検査は、数分以内に終わる（CI の時間制限）
- シークレットは使わない。検査の job の権限は `contents: read`（ラベルを自動で外す job の権限は、Round 2 の Q6）
- **正直な限界（人間が了承。Q4）**: この検査自体が、ブランチの中の `.github/workflows/` で動くので、AI がそのファイルを書き換えれば、検査ごと消せる。ブランチ保護が無い限り、完全な防御ではない。それでも、変更が差分に残り（AC-4 で、赤になる）、人間が読む。本当の壁は、段階4の `permissions.deny` と、人間の目
- 比較用に、`origin/main` のコードでテストを収集する（依存が入った環境で、`pytest --collect-only`）。収集は、テストを実行しない
