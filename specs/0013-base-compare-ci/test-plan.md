# test-plan（0013 base-compare-ci / サイズ: S2）

S2は観点カタログ（`specs/_catalog/viewpoints.md`）を全行評価する。
「適用しない」には必ず理由を書く。AIが自信のない行は `⚠️` を付けて目立たせる（G2で人間が見る）。
ここは「テストのリスト」まで。テストコードは1件ずつ、Red→Greenで書く。
期待値は、`req.md` の人間の例から取る。空欄の期待値は、`discussion-log.md` の Round 2 の回答待ち。

対象は、「`origin/main` と HEAD を比べ、検出（理由つき）の一覧を出し、承認の有無と合わせて、緑・赤・警告を決める」検査。判定の本体（`change_reason_for`）は 0012 でテスト済みの純粋関数を、そのまま使う。ここでは、「差分の集め方、ID の比較、承認の扱い、結果の出し方」をテストする。

| 観点 | 適用/適用しない | 具体例 | 理由 | 対応するAC |
| --- | --- | --- | --- | --- |
| V-01 空 | 適用 | (a) `origin/main` と HEAD が同じ（差分が空）→ 緑。(b) 空のテストファイルを足しただけ → 緑。(c) 収集されるテストが 0 件と 0 件 → 緑 | 差分が無い PR は、普通にある。空を「異常」と誤検出しない | AC-1, AC-3 |
| V-02 0・負数・最大値・最大+1 | 適用 | (a) 基準で 1 件のテストを、いま 0 件にした（全部消えた）→ 赤。(b) 基準で 0 件、いま 1 件 → 緑（足すのは自由）。(c) 変更ファイル数が 0 件／1 件／多数（境界は、実装時に決める。上限は無いので、時間で見る） | 「全部消えた」は、最も重大な減り方。0 件との境界で、比較が壊れないこと | AC-3 |
| V-03 型違い・全角・絵文字・改行 | 適用 | (a) パスやテスト ID に、日本語・絵文字・改行・空白を含む（`tests/テスト_🍎.py`、`test_a[１２３]`）→ 例外にならず、正しく比較される。(b) CRLF のテストファイル → 変更なしなら緑 | `git diff` と pytest の出力の読み取りは、文字の扱いで壊れやすい。壊れたら、ツール自身の失敗（赤）になるので、先に確かめる | AC-1, AC-3, AC-2 |
| V-04 巨大な入力 | 適用 | (a) 巨大なテストファイル（60万文字超）の追記 → `change_reason_for` の巨大ファイル経路で、緑。書き換え → 赤。(b) 変更ファイルが非常に多い、テスト ID が非常に多い → 時間内に終わるか、時間切れなら、ツール自身の失敗（赤）。承認ラベルがあっても赤 | CI は数分以内（制約）。時間切れは、人間が決めた「ツール自身の失敗」 | AC-2, AC-3 |
| S-01 対象が存在しない | 適用 | (a) `origin/main` が無い（取れない）→ CI は赤、ローカルは警告（⚠️ Q7）。(b) merge-base が無い（履歴が浅い、無関係の履歴）→ ツール自身の失敗。(c) 基準にファイルが無い（新規）→ 検出しない。(d) HEAD でファイルが消えた → `change_reason_for` は呼ばない（削除は、AC-3 の ID の消失で見る） | 「基準が取れない」は、検査の前提が崩れる最も重要なケース。0012 で決めた、新規・削除の扱いと、つながる | AC-2, AC-6 |
| S-02 重複 | 適用 | (a) 同じテスト関数を2つ定義した（後ろが前を上書き）。ID の一覧は1つになる → 基準より減っていれば赤（既存の比較でも検出される）。(b) 同じ ID が、基準の収集結果に2回出る → 重複を数えず、集合で比べる | 重複 ID があっても、比較が壊れない（件数でなく集合で見る、という Q3=B の核心） | AC-3 |
| S-03 同じ操作の繰り返し | 適用 | (a) 同じコードで、検査を2回実行 → 同じ結果。(b) 同じコードで、テストを2回収集 → ID の一覧が同じ（人間の AC）。違えば、ツール自身の失敗。(c) 承認ラベルを、付ける・外す・付ける → 最後の状態で決まる | 冪等でない検査は、赤・緑が揺れて、信頼されなくなる。人間が、受け入れ条件に入れた | AC-3, AC-5 |
| S-04 別の対象が互いに影響しない | 適用 | (a) 2つの PR があり、片方にだけ承認ラベルがある → もう片方は、承認されない（PR ごと）。(b) 1つの PR に、承認できる検出（テスト）と、承認できない検出（ツール自身の失敗）が混ざる → 赤（承認できないものが残る）。(c) 複数ファイルの検出が、1つのファイルの承認で、全部通る ⚠️ | 承認が、別の PR・別の検出に波及しないこと。(c) は、ラベル1つの設計（Q8）の結果 | AC-5 |
| X-01 未認証・権限なし | 適用 | (a) 検査の job のトークン権限は `contents: read` のみ（ワークフローを読んで確かめる）。(b) 承認ラベルを外す job にだけ、`pull-requests: write` ⚠️（Q6）。(c) シークレットを使わない | 権限の最小化。人間が、制約に入れた。ラベルを付けられる人（AI は不可）は、`settings.json` の別の req | AC-5 |
| X-02 他人のデータ | 適用 | (a) 承認ラベルを、PR 番号で読む。別の PR のラベルを読まない（イベントの PR 番号を使う）。(b) 別のリポジトリ（fork）の PR のラベル → このリポジトリは個人利用で fork を想定しないが、イベントのリポジトリが違えば、承認として扱わない | 他人の承認で通ってしまうのが、いちばん悪い失敗。PR 番号とリポジトリの取り違えを、テストで確かめる | AC-5 |
| X-03 危険な文字列（SQL・パス・コマンド） | 適用 | (a) パスに `; rm -rf`、`$(touch x)`、`../../etc/passwd`、改行を含むファイルを変更 → 実行されず、検出（または、ツール自身の失敗）として扱われ、パスは、そのまま文字列で表示される。(b) ブランチ名・PR タイトルに `"; echo`、`$(...)` → workflow の `run:` に、直接埋め込まない（環境変数で渡す） | CI の、スクリプトインジェクションの典型。`git` や `pytest` を呼ぶときは、引数のリストで渡し、シェルを通さない | AC-1, AC-3, AC-5 |
| X-04 エラーに内部情報が出ない | 適用 | (a) ツール自身の失敗の表示に、トークン、環境変数、絶対パス（ホームのパス）、スタックトレース全体を出さない。(b) 要約には、ファイルの相対パスと理由だけ出す | CI のログは、リポジトリの閲覧者に見える。トークンが出たら、致命的 | AC-2, AC-5 |
| O-01 エラー形式の統一 | 適用 | (a) すべての検出を、同じ形式（ファイル、種類、理由、承認できるか）で出す。(b) 終了コードの決まり（緑 / 検出 / ツール自身の失敗）⚠️ | CI の要約と、ローカルの警告を、同じ部品で作れる。終了コードは、req に決めが無い（Q7 と合わせて決める） | AC-5, AC-6 |
| O-02 金額の丸めと単位 | 適用しない | — | 金額・単位が無い（ファイルの比較） | — |

## テストの順序（1件ずつ進める）
置き場所（`tools/` か `.claude/hooks/guardlib/` か）と、入口の形は、実装時に決める。テストは `tests/` に置く。⚠️ の行は、Round 2 の回答後に、期待値を確定する。
1. 差分が空 → 緑（V-01a、AC-1）
2. 既存のテストの期待値を書き換えた → 赤（AC-1）
3. テストを足しただけ → 緑（AC-1）
4. pytest の設定を変えた → 赤（AC-1）
5. 基準にあった ID が、いま無い → 赤。件数が同じでも赤（AC-3）
6. 基準の全部が消えた → 赤（V-02a）
7. 同じコードで2回収集 → ID の一覧が同じ（S-03b、AC-3）。違えば、ツール自身の失敗
8. 守りの仕組み自体の変更（`.github/**`、Makefile など）→ 赤、承認で通せる（AC-4）
9. 承認ラベルあり → 検出が緑になり、要約に、何を承認したかが出る（AC-5）
10. 承認ラベルなし → 赤（AC-5）
11. ツール自身の失敗（`tool = 1` で例外、タイムアウト）→ ラベルがあっても赤（AC-2）
12. push だけのとき、比較の検査は動かない。pull_request のとき動く（AC-6）
13. ローカルでは、検出があっても警告だけ（AC-6）
14. 新しいコミットで、承認ラベルが外れる。`labeled` / `unlabeled` で再実行される（AC-5）
15. 危険な文字列のパス、日本語・絵文字のパス、巨大な入力（X-03、V-03、V-04）
16. ⚠️ の行（Q6〜Q9 の回答後に確定）: 承認ラベルを外す権限、ローカルのツール失敗、ラベル1つか2つか、解析しきれない入力の承認

迷いどころは、このファイルに書かず `discussion-log.md` の新しいRoundに質問として書く（表の `⚠️` 行はその回答待ち）。
