# 議論ログ（0013 base-compare-ci）

AIと人間のやりとりを、ここに積む（ファイルは分けない）。
- 質問: 1ラウンド最大5問。答えなければ「推奨」で進む。足りなければ Round を積む。
- フィードバック: `## FB 1`、`## FB 2` と積む。`/req-fb` が読んで差分だけ直す。
- 回答は「回答:」の行に、選択肢の記号か自由記述で書く。
- AIの回答: 質問の回答やFBに対応したら、その直後に `### AI回答（FB n）`（質問なら `### AI回答（Round n）`）を書く。チャットの説明は要約にして、正本はここに置く。

前提（人間がすでに決めたこと。質問しない）:
- 比較の基準は `origin/main`（merge-base）。同じ検査を、CI と、`make check`（ローカル）でも動かせる形にする。
- ブランチ保護・必須チェックは使えない（非公開の Free プラン）。赤のままマージしないのは、運用で守る。マージは人間だけ。
- AI は、PR を作れるが（`gh pr create`）、PR のラベルを付けることや、`gh api` は使えない（段階4のあとの設定案）。

## Round 1

### Q1. 検査が問題を見つけたとき、CI はどうする？
- シナリオ: 作業ブランチで、既存のテストの期待値を書き換えた、または、テストが減った、または、比較の関数が例外になった（解析しきれない入力）。push したら、CI がそれを見つけた。
- 選択肢:
  - A. **赤にする**（失敗）。解析しきれない入力・例外も、赤（拒否側に倒す）
  - B. 警告だけ出す（緑のまま。ログに書く）。解析しきれない入力は、赤
  - C. 警告だけ出す。解析しきれない入力も、警告
- 推奨: A
- 推奨の理由: ブランチ保護が使えず、マージを止める仕組みは、人間の目だけ。緑のままだと、見落とす。赤なら、Actions の一覧に必ず出る。セキュリティが最優先なので、判断できないものは、拒否側に倒す（hook と同じ方針）。誤検出の負担は、Q2 の承認で逃がす。
- 回答: 

### Q2. 正当な変更（仕様が変わって、期待値を直した）は、どうやって通す？
- シナリオ: 人間が、仕様変更に伴って、既存のテストの期待値を意図して直した。CI は赤になる（Q1 が A の場合）。承認の記録が、AI が書き換えられない場所に要る（作業ブランチの中に書くものは、AI が偽造できる）。
- 選択肢:
  - A. **PR のラベル** `test-change-approved` を、人間が GitHub の画面で付ける。CI は、PR のラベルを読み、付いていれば、見つけた変更を「承認済み」として緑にする（`pull_request` のときに動く検査が、ラベルを見る）。AI は、ラベルを付けられない（`gh api` を deny するため）
  - B. コミットメッセージに `Test-Change-Approved: 理由` の行を、人間が書く。CI は、その行を探す。AI も書けてしまうが、人間は、マージ前に差分を読む
  - C. 承認の仕組みは作らない。赤のまま、人間が理由を確認して、マージする（例外運用）
- 推奨: A
- 推奨の理由: 承認が、ブランチの外（PR のラベル）に残るので、AI が偽造できない。B は偽造できる（AI がコミットを書くため）。C は、「赤のままマージしない」運用と矛盾し、赤に慣れてしまう。A の費用は、PR を経由すること（push だけの運用では、使えない）。ラベルは、Free プランの非公開リポジトリでも使える。
- 回答: 

### Q3. 「テストが減っていないか」は、何で見る？
- シナリオ: 作業ブランチで、`test_b` を消して、別の `test_new` を足した（件数は同じ）。または、Makefile の `test:` から `tests` を外して、収集される件数が減った。
- 選択肢:
  - A. **収集されるテストの件数**（`pytest --collect-only`）が、`origin/main` より減ったら、検出
  - B. **収集されるテストの ID の一覧**を比べて、`origin/main` にあって、いまは無い ID があれば、検出（件数が同じでも、消した・名前を変えたものは見つかる）
  - C. AST（既存の比較）だけで見る。件数・ID は見ない
- 推奨: B
- 推奨の理由: A は、「消して、別のを足す」を見逃す。C は、Makefile の `test:` を変えて収集から外す（0008 の A2 の型）を見逃す。B なら、どちらも見つかる。弱点は、名前を変えただけでも検出されること（誤検出）。それは Q2 の承認で通せる。セキュリティ ≥ 保守性の優先順位に合う。
- 回答: 

### Q4. どのファイルの変更に、承認を求める？
- シナリオ: AI が、CI の設定（`.github/workflows/check.yml`）を書き換えて、検査を飛ばす。または、Makefile の `check` から検査を外す。
- 選択肢:
  - A. テストに関するものだけ: 既存のテスト、conftest、pytest の設定、Makefile の `test:`、実装中の req.md の AC の表
  - B. A に加えて、**守りの仕組み自体**: `.github/**`、`.claude/**`、`tools/guard-equiv/**`、`Makefile`、`CLAUDE.md`、`specs/README.md`、`specs/_catalog/**` の変更は、すべて承認が要る
- 推奨: B
- 推奨の理由: 検査を飛ばす最短の道は、検査の設定を書き換えること。B なら、それも、赤になる。ただし、正直な限界がある: **この検査自体が、ブランチの中の `.github/workflows/` で動くので、AI がそのファイルを書き換えれば、検査ごと消せる**（ブランチ保護が無い限り、完全な防御ではない）。それでも、「消した」という変更が、差分に残り、人間が読む。B は、その差分を見つけやすくする（赤にはならなくても、ログに出る）。段階4の `permissions.deny` と、人間の目が、本当の壁になる。
- 回答: 

### Q5. 仕様の項目に、対応するテストがあるか（AC番号の対応）は、この req に含める？
- シナリオ: 仕様に AC-4 があるのに、AC-4 のテストが無い（0008 の A4 の型）。これを機械で見つけたい。ただし、「テストが AC 番号を参照する約束」が、まだ無い（`/req-new` の「期待値の出所」の列とセットで、別の req として入れる、という人間の指示がある）。
- 選択肢:
  - A. この req には含めない。約束を入れる req を先にやり、そのあとの req で、この検査を足す
  - B. この req に含める。約束（テストの docstring や marker に AC 番号を書く）も、この req で決める
- 推奨: A
- 推奨の理由: 約束が無いまま検査だけ作ると、既存のテストが全部「対応なし」になって、赤が止まらない。約束は `/req-new` と `/req-run` の流れ（skills、保護対象）も変えるので、この req の範囲（比較と CI）より大きい。この req は、A のまま、Q1〜Q4 に集中したほうが、小さく終わる。
- 回答:
